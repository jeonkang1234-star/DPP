# 영지식증명(ZKP) 프로토타입 - 실행 가이드

## 어떤 라이브러리를 썼나

**o1js** (버전 2.15.0) — Mina Protocol이 만든, 순수 TypeScript/JavaScript로 짜인 zk-SNARK 라이브러리.

원래는 circom + snarkjs(가장 널리 쓰이는 표준 조합)를 쓰려고 했는데, circom 컴파일러는 Rust 바이너리를 GitHub Release에서 받아야 해서 GitHub 접속이 막힌 환경에서는 설치가 불가능했음. o1js는 `npm install`만으로 끝나서 그 문제를 피해갈 수 있었음.

**o1js가 뭔지 한 줄로:** "증명하고 싶은 조건(예: C ≤ 0.24wt%)"을 JS 함수로 적으면, 그 함수를 실행했다는 증명(proof)을 만들어주는 라이브러리. 증명에는 계산에 쓰인 값(측정치 180 같은 실제 수치)은 안 들어가고, 조건을 비교한 결과만 들어감.

- 내부적으로 Kimchi/Pickles라는 증명 시스템(zk-SNARK의 한 종류, Groth16/PLONK 계열과 같은 급)을 씀
- 원래는 Mina 블록체인의 스마트컨트랙트(zkApp)용 라이브러리지만, 블록체인 없이 증명 생성/검증 로직만 떼어내 써도 됨 (이 프로토타입이 그렇게 쓴 것)

## 파일 구성

| 파일 | 역할 |
|---|---|
| `circuits.mjs` | **본체.** judge.py의 8개 문서유형(evaluate_*)에 대응하는 8개 ZKP 회로 정의 |
| `logic_only_check.mjs` | 회로 안의 비교식만 떼어내 즉시(1초 내) 검증 - 스케일링/경계값 로직만 확인, 증명은 생성 안 함 |
| `analyze_check.mjs` | 회로 8개를 실제로 빌드(제약조건 시스템 생성)해서 타입/구조 오류 확인 - 신뢰설정은 생략해서 비교적 빠름(수초~수십초) |
| `test_all.mjs` | **진짜 증명.** 8개 회로 전부 compile→prove→verify까지 실행하고 judge.py 판정과 대조. 가장 오래 걸림(회로당 수십초~수분, PC 사양에 따라 다름) |
| `circuit_batch.mjs` | 이전 프로토타입(제강성적서 단독, assert형 설계) - 이번 확장판(`circuits.mjs`)이 그 자리를 대체함. 참고용으로 남겨둠 |

## 이번에 새로 한 것 (지난 대화 이후 확장)

기존에는 제강성적서 1개 문서유형만 프로토타입으로 증명했음. 이번에 **judge.py가 판정하는 34개 항목 중 30개**를 문서유형별로 8개 회로에 나눠서 전부 회로화함.

### 설계를 하나 바꿨음: Assert형 → Boolean 출력형

기존 프로토타입은 "조건을 만족해야만 증명이 생성되는" assert형이었음. 이 방식대로 34개 전체를 확장하면 **부적합(FAIL) 판정 문서는 증명 자체가 안 만들어지는** 문제가 있음 (실제로 배터리 재생원료 Co, 재활용효율 코발트 등은 mock 데이터에서도 진짜로 FAIL임). 그래서 모든 회로를 **"조건 충족 여부(참/거짓)를 공개 출력값으로 리턴"**하는 방식으로 바꿈. 적합/부적합 어느 쪽이든 정상적으로 증명이 만들어지고, 검증자는 참/거짓만 보되 측정값은 여전히 비공개.

### 회로 8개 = judge.py 문서유형 8개

| 회로 | 문서유형 | 포함 항목 | 개수 |
|---|---|---|---|
| SteelMillCheck | Q2_05 제강성적서 | 화학성분 8종 + 기계적성질 4종 | 12 |
| CbamCheck | Q2_06 CBAM | 연간누적 수입수량 de minimis | 1 |
| FiberSumCheck | Q1_04 섬유케어라벨 | 혼용률 합계 ≈100% | 1 |
| OekotexCheck | Q3_10 OEKO-TEX | pH | 1 |
| BatteryCheck | Q2_07 배터리PCF | 재생원료 Co/Li/Ni/Pb + 탄소발자국 선언의무 용량플래그 | 5 |
| RecyclingCheck | Q4_15 재활용처리결과 | 구리 + 리튬/코발트(파생) | 3 |
| RohsCheck | Q2_04 RoHS | Pb/Cd/Hg/Cr6+/PBB/PBDE | 6 |
| CeMarkingCheck | Q3_09 CE마킹 | 최소 높이 | 1 |
| **합계** | | | **30** |

### 이번에 회로화 안 한 4개 항목 (judge.py엔 있지만 ZKP 대상 아님)

전부 "단순 수치 임계값 비교"로 환원이 안 되는 항목이라서 뺐음. mock 데이터나 파서 문제가 아니라 판정 로직 자체가 회로에 안 맞는 구조라 제외한 것:

- **CBAM 내재배출량** — 기준값 자체가 없는 정보성 항목 (judge.py도 항상 "판정 대상 아님"만 리턴)
- **섬유명칭 Annex I 유효성** — 수치 비교가 아니라 문자열이 목록에 있는지 대조하는 로직. 회로화하려면 멤버십 증명(머클트리 등) 같은 다른 설계가 필요함
- **배터리 최대 생애주기 탄소발자국 임계값** — 위임법령 미확정이라 기준값 자체가 없음 (judge.py도 항상 "판정 불가")
- **재활용효율(2025~)** — 소재별 표 합계 vs 입고중량 불일치를 검사하는 "분모 충돌" 로직이 끼어 있어서 단순 임계값 비교가 아님(3중 분기: 적합/미달/판정보류)

## 고정소수점 스케일링

Field(zk-SNARK의 정수 필드)는 소수를 못 다뤄서 전부 정수로 스케일링함:

| 값 종류 | 스케일 | 예 |
|---|---|---|
| 철강 화학성분(wt%, 소수 3자리) | x1000 | 0.18wt% → 180 |
| 철강 기계적성질(이미 정수) | x1 | 382 → 382 |
| CBAM 수입량 / 배터리·재활용 비율 / pH (소수 1자리) | x10 | 62.4t → 624 |
| CE마킹 높이(소수 2자리) | x100 | 6.64mm → 664 |
| RoHS 함량(소수 1자리) | x10 | 252.8mg/kg → 2528 |

## 배터리 Pb의 "적용 제외" 예외 처리

judge.py는 "재생원료 Pb 실측 0% → 적용 제외(EXEMPT)"라는 특수 케이스가 있음(리튬이온전지엔 원래 Pb가 없어서). 이걸 회로에서는 **OR 조건**으로 흡수함:

```
pbOkOrExempt = (측정값 == 0) OR (측정값 >= 기준치)
```

증명이 참이면 "적용제외거나 적합함" 둘 중 하나라는 뜻이고, 어느 쪽인지는 여전히 공개되지 않음(오히려 이게 사생활 보호 측면에서 더 나은 설계 - Pb가 0%인지 자체도 숨겨짐).

## 실행 방법 (3단계 - 아래로 갈수록 오래 걸림)

Node.js 18+ 필요. 처음 한 번만:
```
npm install
```

### 1단계 - 즉시 확인 (1초 내)
```
node logic_only_check.mjs
```
회로 안 비교식과 동일한 계산을 회로 밖에서 그대로 돌려서 스케일링/경계값이 맞는지 확인. 25개 체크 전부 통과해야 정상.

### 2단계 - 구조 검증 (수십 초)
```
node analyze_check.mjs
```
8개 회로를 실제로 빌드(제약조건 시스템 생성)해서 타입 오류·로직 오류가 없는지 확인. 신뢹설정(trusted setup) 단계는 생략해서 빠름.

### 3단계 - 실제 증명 (제일 오래 걸림, PC 사양에 따라 회로당 수십 초 ~ 수 분)
```
node test_all.mjs
```
8개 회로 전부 compile → prove → verify 하고 judge.py의 실제 판정 결과와 자동 대조. 대부분은 실제 mock 데이터 값을 쓰고, mock 데이터에 FAIL 사례가 아예 없는 항목(CBAM/OEKO-TEX/RoHS/CE마킹)은 "[합성]"이라고 표시된 임의 값으로 FAIL 케이스도 확인함 - 실제 문서에서 나온 값이 아니니 헷갈리지 말 것. 배터리 Co, 재활용 코발트는 실제 mock 데이터에 진짜 FAIL 사례가 있어서 그대로 씀.

마지막에 `N개 통과 / M개 실패` 요약이 뜸. 0개 실패가 정상.

## 이 환경(작업 샌드박스)에서 확인한 것 / 못한 것

- **확인함**: 1단계(로직) 25/25 통과, 2단계(구조) 8/8 통과 — 즉 모든 회로의 계산 로직과 타입 구조는 정확함
- **확인 못 함**: 3단계(실제 증명 생성)는 이 작업 환경이 지금 유독 느려서(회로 하나 컴파일에만 100초 넘게 걸림 - 예전엔 훨씬 빨랐음) 시간 제한 안에 끝까지 못 돌렸음. 다만 이전에 제강성적서 12항목 회로는 이 환경에서도(129초) 그리고 사용자님 로컬 PC에서도(24.5초) 이미 실제 증명 생성→검증까지 전부 성공한 전례가 있어서, 이번 8개 회로도 로컬에서 돌리면 정상적으로 끝날 것으로 봄. **3단계(`node test_all.mjs`)는 로컬에서 직접 돌려서 최종 확인해주시면 됨.**
