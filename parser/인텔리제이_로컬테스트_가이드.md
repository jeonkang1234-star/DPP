# DPP 문서 파서 — 인텔리제이 로컬 테스트 가이드

목적: FastAPI로 서비스화하기 전에, **23종 × 10건 = 230개 목데이터 PDF가 문서유형별로 정확히 파싱되는지**를 IntelliJ(파이참 플러그인)에서 직접 실행/디버깅할 수 있게 설계한 테스트.

---

## 1. 전체 구조 요약

```
새 폴더/                          ← IntelliJ 프로젝트 루트로 열면 됨
├── 00_분류근거_및_출처.txt         ← 23종 분류 기준 원문 (registry.py/extractor.py가 이 문서 근거로 작성됨)
├── 노 고정/   (= Q4: 디자인·데이터 둘 다 자유, 8종)
├── 데 고정/   (= Q2: 데이터만 고정, 8종)
├── 디 고정/   (= Q3: 디자인만 고정, 3종)
├── 디, 데 고정/ (= Q1: 디자인·데이터 둘 다 고정, 4종)
└── dpp-doc-parser/
    ├── registry.py      ← 23종 문서 타입 메타데이터 + 파일명 분류 규칙
    ├── splitter.py       ← 합본 PDF 1개(10건 이어붙음) → 개별 문서 10건 분할
    ├── extractor.py      ← 공통 필드 + 문서유형별 확장 필드 추출 (한 파서, 유형별 다른 규칙)
    ├── qr.py / hasher.py ← QR 디코딩 / SHA-256 해시
    ├── pipeline.py       ← 위 전부 엮어서 폴더 전체 처리
    ├── main.py           ← CLI 진입점 (로컬 배치 테스트용)
    ├── api.py            ← FastAPI (실서비스 연동용, **로컬 테스트 단계에서는 실행 안 함**)
    ├── output_v2/         ← main.py로 230건 전체 처리한 기존 결과 (참고용 JSON)
    └── tests/             ← 이번에 추가한 pytest 테스트 (신규)
        ├── conftest.py
        └── test_pipeline.py
```

**"하나의 파서, 유형마다 다른 추출"**은 이미 이 구조로 구현돼 있음: `registry.py`가 파일명→23개 코드 중 하나로 분류하고, `extractor.py`의 `extract_extended_fields(registry_code, text)`가 그 코드에 따라 다른 필드를 뽑는다 (`TYPE_SPECIFIC_EXTRACTORS` 딕셔너리 참고). 새 문서 유형을 추가할 땐 `registry.py`에 항목 추가 + 필요하면 `extractor.py`에 전용 함수만 추가하면 됨.

**FastAPI(`api.py`)는 이번 로컬 검증 범위에 안 넣었음.** `main.py`(배치) / `tests/`(검증)만 로컬에서 돌리고, `api.py`는 이 검증이 다 통과한 다음 단계에서 켜는 것으로 분리해뒀다 (요청하신 2번 항목 그대로).

## 2. IntelliJ 설정

1. **Python 플러그인**이 설치돼 있어야 함 (Ultimate는 기본 포함, Community는 "Python Community Edition" 플러그인 설치).
2. `File > Open`으로 `새 폴더`(이 프로젝트 루트)를 연다.
3. **인터프리터 설정**: `File > Project Structure > SDK` 또는 우측 하단 인터프리터 선택에서 새 venv 생성
   - 위치: `dpp-doc-parser\.venv` (예시)
   - Python 3.10+ 권장 (테스트는 3.10에서 검증함)
4. IntelliJ 터미널(Alt+F12)에서:
   ```
   cd dpp-doc-parser
   pip install -r requirements.txt
   pip install pytest
   ```
5. `dpp-doc-parser` 폴더를 **Sources Root**로 지정 (우클릭 → Mark Directory as → Sources Root). 이렇게 해야 `tests/conftest.py`에서 `import registry` 등이 IntelliJ 코드 분석기에서도 빨간줄 없이 인식됨.

### Run Configuration (pytest)

- `Run > Edit Configurations > + > Python tests > pytest`
- Target: `Script path` → `dpp-doc-parser/tests` 폴더 지정 (또는 `Module name` 대신 `Custom` → 경로)
- Working directory: `dpp-doc-parser`
- 저장 후 `tests/test_pipeline.py` 아무 테스트 함수 왼쪽의 ▶ 버튼으로 개별 실행/디버깅 가능

`conftest.py`는 자기 위치에서 위로 올라가며 `노 고정/데 고정/디 고정/디, 데 고정` 4개 폴더가 있는 지점을 자동으로 찾으므로, 프로젝트 루트를 `새 폴더`로 열든 `dpp-doc-parser`만 열든 상관없이 동작한다.

## 4. 문서유형마다 뭐가 다르게 파싱되는지 (테스트가 검증하는 것)

## 6. 알려진 한계 (다음 단계 전에 알고 있어야 할 것)

- `Q1_01`(EUR.1), `Q3_09`(CE마킹), `Q3_10`(OEKO-TEX), `Q4_12`(CoC 추적서)는 표 형태/조항 나열형 텍스트라 확장 필드(지표·섹션)가 지금 정규식으로는 안 잡힘. 좌표 기반 파싱(pdfplumber)이 필요한 영역이라 의도적으로 손대지 않은 상태.
- 23종 문서의 법적 요구 세부항목을 전부 구조화하는 건 아니고, "뽑히면 확실히 맞는 것만" 뽑는 원칙(README 참고).
- 이 테스트는 `output_v2/`의 기존 결과와 별개로, `tests/`가 원본 PDF를 다시 열어 파싱 로직 자체를 재검증한다 — 즉 "이전에 만들어둔 JSON이 맞다"가 아니라 "코드가 지금도 맞게 동작한다"를 확인하는 것.

## 7. 다음 단계 (이 테스트 통과 이후)

로컬 pytest가 계속 초록불이면, `api.py`를 `uvicorn api:app --reload`로 띄워 FastAPI 엔드포인트(`/health`, `/registry`, `/parse`)를 Postman 등으로 별도 검증한 뒤 Spring Boot BE와 연동하면 됨 (README의 "HTTP 서비스로 실행" 절 참고). 로컬 테스트 단계에서는 이 부분은 실행하지 않는다는 요청대로 이번 검증에는 포함하지 않았다.
