# 도메인별 목데이터 PDF (52건)

화면에서 **한 건씩 업로드해서 승인/반려를 바로 테스트**할 수 있는 개별 PDF 세트다.
파일명에 PASS/FAIL이 붙은 문서는 실제로 업로드하면 그 판정이 나온다.

## 2026-08-19 재생성 — 무엇이 바뀌었나

`requirement_field`가 'DPP_데이터항목_분류.xlsx'의 T0(법정필수)·T1(조건부필수) 기준으로
재구축되면서, 문서에서 뽑아야 할 항목이 26개에서 **192개**가 됐다. 이전 세트에는 그 항목들이
문서 어디에도 없어서, 파서가 아무리 정확해도 입력 화면의 자동 채움 칸은 계속 비어 있었다.

그래서 모든 문서에 **부속서 A — 디지털 제품여권 데이터 항목**을 붙였다.

- 항목 라벨은 손으로 적지 않고 `parser/spec_fields.py`(= requirement_field 시드)에서 가져온다.
  손으로 적었다면 시드가 바뀌는 순간 조용히 어긋났을 것이다.
- 부속서는 `라벨 : 값`을 **한 줄에** 쓴다. 표로 그리면 PyMuPDF가 라벨과 값을 다른 줄로
  쪼개는데, 그러면 (1) 라벨 사전 파서가 아무것도 못 뽑고 (2) 케어라벨의 섬유조성 파서가
  '짧은 라벨 + N %'를 섬유 항목으로 오인한다.
- 본문(성적서 표, 케어라벨 조성, OEKO-TEX 시험표 등)은 이전 세트의 줄 구조를 그대로 지켰다.
  `parser/extractor.py`의 타입별 파서가 줄 오프셋으로 읽기 때문에 한 줄만 어긋나도 ZKP 판정이
  통째로 깨진다.

## 사용법

각 도메인 폴더에서 파일 하나씩 골라 해당 업로드 슬롯에 넣는다. 파일명에 PASS/FAIL이 없는 건
ZKP 판정 대상이 아닌 문서(형식만 갖추면 업로드 즉시 승인)라 1건씩만 있다.

### steel/ (16건)
- `Q2_05_MILL_SHEET_PASS_1/2.pdf`, `FAIL_1(탄소초과)/2(인장강도초과).pdf` — 제강 성적서.
  화학성분 8개(C/Si/Mn/P/S/N/Cu/CEV) + 기계성질 4개(ReH/Rm/A/KV)가 전부 성적서에 인쇄된
  규격 이내여야 승인. 부속서에 미량원소(Cr/Ni/Mo/Zr/Ce/W/Co/Sb/Zn)와 시험표준·표점거리까지 실었다.
- `Q2_06_CBAM_REPORT_승인_수입량초과/미만.pdf` — CBAM은 de minimis(50t) 초과 여부가
  **정보성 플래그**라 반려 케이스 자체가 없다. 그래서 PASS/FAIL이 아니라 수입량 두 상태로 나눈다.
  부속서에 전구체 3종·전력 배출계수·제3자 검증 정보가 들어 있다.
- `DOC_*.pdf` 10종 — 비-ZKP 문서. `DOC_SOC_SDS`에 SVHC/RoHS/6가크롬, `DOC_COO`에 원산지증명서 URL.

### textile/ (18건)
- `Q1_04_CARE_LABEL_PASS_1/2.pdf`, `FAIL_1(합계90)/2(합계110).pdf` — 혼용률 합계가
  100%±0.5%p 안이어야 승인. 부속서에 겉감/안감/충전재 BOM 16항목.
- `Q3_10_OEKOTEX_LABEL_PASS_1/2.pdf`, `FAIL_1(pH초과)/2(pH미달).pdf` — pH 4.0~7.5여야 승인.
  부속서에 SVHC 10종(실제 REACH 후보목록 물질명·CAS)과 포장재 중금속 시험 결과.
- `DOC_*.pdf` 10종.

### battery/ (18건)
- `Q2_07_BATTERY_CARBON_PASS_1/2.pdf`, `FAIL_1(Co미달)/2(Pb미달).pdf` — 재생원료
  Co≥16.0% / Li≥6.0% / Ni≥6.0% / Pb≥85.0%(단 Pb=0%면 적용제외) 전부 충족해야 승인.
  부속서에 셀 화학·구성 16항목 + CRM 함유량 18항목.
- `Q4_15_RECYCLING_REPORT_PASS_1/2.pdf`, `FAIL_1(리튬코발트미달)/2(구리미달).pdf` — 구리
  회수율≥90.0% AND 리튬코발트산화물 회수율≥90.0%(코발트 파생)이어야 승인.
- `DOC_*.pdf` 10종. `DOC_TECH_FILE`에 성능·내구성 24항목, `DOC_SOC_SDS`에 SVHC 3종.

## 재생성 / 검증

```
python3 docker/mock-documents/generator/build.py     # 52건 재생성
python3 docker/mock-documents/generator/verify.py    # 실제 파서·판정으로 검증
```

`verify.py`가 검사하는 것 4가지. 하나라도 실패하면 종료 코드가 0이 아니다.

1. **텍스트 추출** — 운영 고정 버전(PyMuPDF 1.24.9)으로 글자가 나오는가.
2. **ZKP 판정** — 파일명의 PASS/FAIL이 `parser/judge.py`의 실제 판정과 일치하는가.
   판정 기준은 BE의 `specPassed` 규칙을 그대로 따른다(문서 유형마다 다르다 - verify.py 주석 참고).
3. **필드 추출** — 문서마다 `spec_extractor`가 뽑아낸 field_code 수.
4. **도메인 커버리지** — 그 도메인의 파서 대상 필드가 전부 어느 한 문서에는 실려 있는가.
   현재 철강 57/57, 섬유 61/61, 배터리 78/78.

빌드에는 한글 TrueType 폰트가 필요하다(`fonts-nanum` 등). reportlab의 UnicodeCIDFont는
폰트를 임베드하지 않고 '표준 CJK 폰트 참조'만 남겨서, 운영 고정 버전 PyMuPDF가 텍스트를
단어 중간에 공백이 끼는 형태로 깨뜨린다 — 2026-08-16에 배터리 문서 전체가 이 문제로
"텍스트를 추출하지 못했습니다"가 됐던 적이 있다. `generator/render.py`가 실제 .ttf를
찾지 못하면 어떤 패키지를 깔면 되는지 알려주고 종료한다.

## 알려진 한계

- `DOC_COO.pdf`의 문서번호가 `EUR1`로 잘려 뽑힌다. `extractor.py`의 EUR.1 패턴이 하이픈에서
  끊기기 때문인데, 이전 세트부터 있던 동작이라 이번 재생성에서 손대지 않았다(문서가 아니라
  파서 쪽 패턴 문제라 고치려면 별도 변경이 필요하다).
- `Q4_15` 재활용 보고서도 같은 이유로 문서번호가 안 뽑힌다(`^보고서 ...`가 줄 시작이 아니다).
- `judge.py`는 규정 해석상 알아둘 값이 있는 항목을 전부 돌려주므로, 케어라벨의 '섬유명칭
  Annex I 유효성'처럼 승인/반려를 가르지 않는 '부적합 의심' 항목이 섞여 나온다. BE가 실제로
  반려에 쓰는 항목은 더 좁고, verify.py는 그 좁은 기준을 검사한다.
